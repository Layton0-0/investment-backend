# 기술 스펙 변경 시 성능 영향 분석

## 현재 기술 스택

### 핵심 기술
- **Java**: 17
- **Spring Boot**: 3.2.2
- **Redis**: 캐싱 및 실시간 데이터
- **WebFlux**: 비동기 처리
- **HikariCP**: 커넥션 풀 (max: 10, min: 5)
- **Circuit Breaker**: Resilience4j

### 성능 요구사항
- API 응답 시간: 평균 500ms 이하, 95%ile 1초 이하
- 주문 실행 시간: 2초 이하
- 종목 분석 시간: 3초 이하
- 초당 요청 처리: 최소 50 TPS
- 동시 사용자: 최소 10명

## 스펙 변경 시나리오별 영향 분석

### 1. Java 버전 다운그레이드 (17 → 11)

#### 영향도: ⚠️ **중간** (5-15% 성능 저하)

**성능 영향**:
- **GC 성능**: Java 17의 ZGC/G1GC 개선사항 손실
  - 예상 영향: GC pause 시간 10-20% 증가
- **컴파일러**: Java 17의 C2 컴파일러 최적화 손실
  - 예상 영향: CPU 사용률 5-10% 증가
- **메모리**: Java 17의 메모리 효율성 개선 손실
  - 예상 영향: 메모리 사용량 5-10% 증가

**실제 영향**:
- API 응답 시간: 500ms → **550-575ms** (약간 증가)
- 처리량: 50 TPS → **45-47 TPS** (약간 감소)
- **결론**: 요구사항은 여전히 충족 가능하나 여유도 감소

**권장사항**:
- ✅ Java 11도 충분히 사용 가능 (요구사항 충족)
- ⚠️ Java 8은 권장하지 않음 (성능 저하 + 보안 이슈)

---

### 2. Spring Boot 버전 다운그레이드 (3.2.2 → 2.7.x)

#### 영향도: ⚠️ **중간** (10-20% 성능 저하)

**성능 영향**:
- **네이티브 컴파일**: Spring Boot 3.x의 GraalVM 지원 손실
  - 예상 영향: 시작 시간 30-50% 증가, 메모리 사용량 10-15% 증가
- **성능 개선**: Spring Boot 3.x의 최적화 손실
  - 예상 영향: 요청 처리 시간 10-15% 증가
- **WebFlux**: Spring Boot 3.x의 리액티브 스택 개선 손실
  - 예상 영향: 동시 처리량 15-20% 감소

**실제 영향**:
- API 응답 시간: 500ms → **550-600ms** (요구사항 근접)
- 처리량: 50 TPS → **40-45 TPS** (요구사항 미달 가능성)
- **결론**: 요구사항 충족이 불안정해질 수 있음

**권장사항**:
- ⚠️ Spring Boot 2.7.x는 최소 요구사항 수준
- ❌ Spring Boot 2.5 이하는 권장하지 않음

---

### 3. Redis 제거 (캐싱 없음)

#### 영향도: 🔴 **높음** (50-200% 성능 저하)

**성능 영향**:
- **DB 부하 증가**: 모든 요청이 DB로 직접 전달
  - 예상 영향: DB 쿼리 수 10-20배 증가
- **응답 시간 증가**: 캐시 미스 시 DB 조회 필요
  - 예상 영향: 응답 시간 200-500ms 증가
- **동시 처리량 감소**: DB 커넥션 풀 고갈 가능
  - 예상 영향: 처리량 50-70% 감소

**실제 영향**:
- API 응답 시간: 500ms → **700-1000ms** (요구사항 초과)
- 처리량: 50 TPS → **15-25 TPS** (요구사항 미달)
- DB 커넥션: 10개 → **부족 가능성 높음**
- **결론**: ❌ **요구사항 충족 불가능**

**대안**:
- ✅ **인메모리 캐싱 (Caffeine)**: Redis 대신 사용 가능
  - 성능 영향: 30-50% 저하 (Redis보다는 나쁘지만 허용 가능)
- ✅ **로컬 캐시**: 애플리케이션 내부 캐싱
  - 성능 영향: 40-60% 저하

**권장사항**:
- 🔴 **Redis 제거는 권장하지 않음**
- ✅ 최소한 인메모리 캐싱은 필수

---

### 4. WebFlux 제거 (동기 처리로 전환)

#### 영향도: ⚠️ **중간-높음** (20-40% 성능 저하)

**성능 영향**:
- **동시 처리량 감소**: 스레드 풀 기반 처리로 전환
  - 예상 영향: 동시 처리량 30-40% 감소
- **외부 API 호출**: 블로킹 방식으로 전환
  - 예상 영향: 외부 API 대기 시간 동안 스레드 점유
- **리소스 사용**: 스레드당 메모리 사용량 증가
  - 예상 영향: 메모리 사용량 20-30% 증가

**실제 영향**:
- API 응답 시간: 500ms → **550-600ms** (약간 증가)
- 처리량: 50 TPS → **30-35 TPS** (요구사항 미달 가능성)
- 메모리: 기본값 → **+20-30%**
- **결론**: ⚠️ 요구사항 충족이 불안정해질 수 있음

**대안**:
- ✅ **CompletableFuture**: 비동기 처리 유지
  - 성능 영향: 10-15% 저하 (WebFlux보다는 나쁘지만 허용 가능)

**권장사항**:
- ⚠️ WebFlux 제거 시 CompletableFuture로 대체 권장
- ❌ 완전 동기 처리로 전환은 권장하지 않음

---

### 5. HikariCP 커넥션 풀 축소

#### 영향도: ⚠️ **중간** (요청 대기 시간 증가)

**현재 설정**:
```yaml
maximum-pool-size: 10
minimum-idle: 5
```

**변경 시나리오**:
- **5개로 축소**: maximum-pool-size: 5
  - 예상 영향: 동시 요청 시 대기 시간 증가
  - 실제 영향: 처리량 30-40% 감소

**실제 영향**:
- 처리량: 50 TPS → **30-35 TPS** (요구사항 미달 가능성)
- 응답 시간: 500ms → **600-800ms** (대기 시간 포함)
- **결론**: ⚠️ 요구사항 충족이 불안정해질 수 있음

**권장사항**:
- ✅ 최소 8개는 유지 권장
- ⚠️ 5개 이하는 권장하지 않음

---

### 6. Circuit Breaker 제거

#### 영향도: 🟡 **낮음-중간** (장애 시 영향)

**성능 영향**:
- **정상 상황**: 성능 영향 거의 없음 (0-2%)
- **장애 상황**: 외부 서비스 장애 시 전체 시스템 영향
  - 예상 영향: 장애 전파로 인한 전체 시스템 다운 가능

**실제 영향**:
- 정상 시: 성능 영향 없음
- 장애 시: 시스템 가용성 99% → **95% 이하** (요구사항 미달)

**권장사항**:
- ✅ 정상 상황에서는 성능 영향 없음
- ⚠️ 장애 대응을 위해 유지 권장

## 결론

**기술 스펙을 낮추면 성능이 떨어집니다.**

다만, **요구사항 수준에 따라 다운그레이드 가능 여부가 결정**됩니다:

- **현재 요구사항 (50 TPS, 500ms)**: 최소 스펙으로도 충족 가능하나 여유도 낮음
- **안정적 운영**: 권장 스펙 유지 권장
- **확장성 고려**: 향후 트래픽 증가 시 권장 스펙 필수

**최소 스펙으로도 동작은 가능하나, Redis 캐싱과 비동기 처리는 반드시 유지해야 합니다.**

## 적용된 성능 최적화 (2026-01-30)

- **대시보드 병렬 로딩**: 잔고·보유·주문·거래설정을 `CompletableFuture`로 병렬 조회. SecurityContext 전파(`runWithAuth`)로 인증 유지. 순차 4회 호출 → 최대 1회 대기 시간 수준으로 단축.
- **현재가 캐시·병렬 조회**: `RealtimeMarketDataService`에 동기 캐시 계층 `getCurrentPriceBlocking(symbol)` 도입 — `@Cacheable`(종목별 5분 TTL)·`@CircuitBreaker` 적용. 단일/다중 종목 모두 동일 캐시 사용. `getCurrentPrices(symbols)`는 `CompletableFuture.supplyAsync`로 종목별 병렬 조회 후 결과 수집. 캐시 미스 시에도 N종목 순차 대기 → 병렬 대기로 응답 시간 단축.
